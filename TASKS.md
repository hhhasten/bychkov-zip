# TASKS.md — завдання для команди

Кожне завдання — самостійний алгоритм із жорстким контрактом. Завдання
спеціально не перетинаються за файлами: команда пише ізольовані модулі, а
інтеграцію у формат `.byz` виконує власник репозиторію.

Правила виконання — в [`AGENTS.md`](AGENTS.md). Якщо правило тут і в
`AGENTS.md` розходиться, діє `AGENTS.md` (крім контракту конкретного
завдання: контракт важливіший).

## Ролі

- **Власник** — `hhhasten`. Єдина людина, яка робить рев'ю та мержить PR у
  `main`. Може змінювати будь-що.
- **Учасник** — усі інші. Пише код своєї задачі, пушить **тільки свою гілку**
  `task/T-XX-...`, відкриває PR у `main`. Не пушить у `main`, не мержить PR,
  не робить force-push у чужі гілки.

## Як видати завдання агенту (для власника)

1. Переконайся, що агент бачить корінь репозиторію (файли `AGENTS.md` і
   `TASKS.md`) і що `origin/main` актуальний.
2. Надішли промпт:

   > Read `AGENTS.md` and `TASKS.md` in the repository root. Complete task
   > **T-01**. Work on a separate branch. Follow the contract literally. Push the
   > branch and open a pull request into `main`, but do not merge it. Finish with
   > a report using the template from `AGENTS.md`.

3. Учасник (або його агент) пушить свою гілку й відкриває PR у `main`.
4. Власник перевіряє звіт, зелений CI і diff, після чого сам мержить PR.
   Учасник PR не мержить.

## Як здати роботу (для учасника)

1. Переконайся, що гілка створена від актуального `origin/main`.
2. Зроби коміти, проганяй `cargo fmt --all`, `cargo test --all-targets`,
   `cargo clippy --all-targets -- -D warnings`.
3. Запуши свою гілку: `git push -u origin task/T-01-lz77`.
4. Відкрий PR у `main`, додай власника рев'юером, дочекайся зеленого
   `CI / check`.
5. Не натискай Merge. Це робить власник.
6. Надішли звіт за шаблоном з `AGENTS.md` (там є рядок `Pull request: <url>`).

Якщо `main` пішов уперед, онови **тільки свою** гілку:

```sh
git fetch origin
git rebase origin/main
git push --force-with-lease
```

Конфлікт у `core/src/lib.rs` вирішується просто: залиш обидва рядки
`pub mod ...;` — свій і чужий.

## Загальні правила для всіх завдань

- Гілка: `task/<ID>-<коротка-назва>`, наприклад `task/T-01-lz77`.
- Дозволені файли: тека завдання `core/src/<module>/**` (нові файли) і
  **рівно один рядок** `pub mod <module>;` у `core/src/lib.rs`.
- Заборонено: `Cargo.toml`, `Cargo.lock`, `format.rs`, `crypto.rs`,
  `archiver/**`, `cli/**`, `huffman/**`, `entropy.rs`, `input.rs`, `path.rs`,
  `error.rs`, `main.rs`, `core/tests/**`, `README.md`, `docs/**`, `AGENTS.md`,
  `TASKS.md`, `.github/**`, `gui/**`.
- Нові залежності не додавати. Тільки `std` і вже підключені крейти.
- Тести — всередині модуля завдання, у `#[cfg(test)] mod tests`.
- Усі публічні функції повертають `crate::error::Result<T>` і використовують
  `crate::error::ByzError`, якщо в контракті не сказано інакше.
- У публічних функціях не використовуй `unwrap()` / `expect()` і не панікуй на
  вхідних даних; у тестах `unwrap()` дозволений. Clippy це не ловить, тому
  перевіряється на рев'ю.
- Перед комітом: `cargo fmt --all`, `cargo test --all-targets`,
  `cargo clippy --all-targets -- -D warnings`. Форматування в CI
  перевіряється командою `cargo fmt --all -- --check`.
- `TASKS.md` заморожений на час спринту: його змінює лише власник, інакше
  учасники працюватимуть із різними версіями контракту.

## Міні-шпаргалка з Rust

Команда не працювала багато з Rust, тому ось мінімум, якого достатньо для цих
завдань.

- `Vec<u8>` — масив, що росте; `&[u8]` — позичена ділянка масиву (даними не
  володіє).
- `usize` — індекс і довжина; `u64` — розмір у байтах. Перетворюй явно:
  `u64::try_from(x)` або `x as u64`, лише коли точно безпечно.
- `Result<T>` — або `Ok(T)`, або `Err(ByzError)`. Оператор `?` повертає
  помилку вгору.
- `Option<T>` — або `Some(x)`, або `None`.
- `enum` може носити дані:
  `enum Token { Literal(u8), Match { distance: u16, length: u16 } }`.
- `#[derive(Debug, Clone, PartialEq, Eq)]` додає відлагодження, клонування й
  порівняння.
- `vec![0u8; 100]` — вектор зі 100 нулів; `Vec::with_capacity(n)` — заздалегідь
  зарезервувати місце.
- `for (i, byte) in data.iter().enumerate()` — індекс і значення.
- `slice[a..b]` — підмасив; `slice.get(a..b)` — безпечна версія, повертає
  `Option`.
- `assert_eq!(a, b)` і `assert!(cond)` — перевірки в тестах.
- Тести лежать у тому самому файлі:
  `#[cfg(test)] mod tests { use super::*; #[test] fn ... }`.
- Запуск тестів одного модуля: `cargo test lz77`.

`cargo fmt --all` сам форматує код — вручну вирівнювати не потрібно.
`unwrap()` у коді бібліотеки заборонений, у тестах — можна.

Контракт у завданні — це точні імена функцій, типів і полів. Їх не можна
перейменовувати чи «покращувати», навіть якщо здається, що так буде зручніше:
за цими іменами код потім інтегрують у ядро.

## Що НЕ входить до жодного завдання

Ці теми залишаються за власником репозиторію, бо вони змінюють формат або
ядро:

- інтеграція LZ77 у `.byz` і вибір прапорців;
- багатотомні архіви й запис томів;
- CRC32 у метаданих і перевірка цілісності під час розпакування;
- PBKDF2 / AES-CTR / HMAC і будь-яка заміна поточної криптографії;
- MLP-класифікатор усередині `create` і вибір алгоритму за типом файлу;
- GA-оптимізація параметрів архіватора;
- CLI-прапорці, GUI, метрика Q, експерименти.

Суміжні рішення, які теж залишаються власнику (щоб не було ілюзій, що
модуль одразу «запрацює» в архіві):

- серіалізація LZ77-токенів у байтовий потік, який приймає Гаффман
  (алфавіт Гаффмана — 256 байтів, а `Token` — це структура);
- шифрування кожного тому окремо: у v1 один заголовок і один GCM-тег на весь
  архів, тому просте розрізання шифротексту на томи не працює;
- формат збереження ваг MLP, навчальні дані й таблиця «клас → стратегія»;
- винесення параметрів архіватора (поріг ентропії тощо) в конфіг, який
  зможе оптимізувати GA;
- рішення, чи потрібен CRC32 у v2, де цілісність уже забезпечує GCM-тег.

Якщо агент пропонує «заодно інтегрувати» — це порушення `AGENTS.md`.

## T-01. LZ77: кодер і декодер

**Гілка:** `task/T-01-lz77`
**Модуль:** `core/src/lz77/mod.rs` (можна розбити на кілька файлів усередині
`core/src/lz77/`)
**Дозволено змінювати:** `core/src/lz77/**`, `core/src/lib.rs` (+1 рядок)
**Нові залежності:** немає

### Що це і навіщо

LZ77 — словникове стиснення без окремого словника. Якщо фрагмент уже
зустрічався раніше, замість нього зберігають пару «на скільки назад
відступити, скільки байтів скопіювати». На цьому тримаються zip, gzip і 7z.
У нашому архіваторі LZ77 стоятиме перед Гаффманом і дасть основне стиснення
текстів, логів і коду.

### Як це працює

Кодер іде по даних зліва направо й тримає вікно — останні 32 768 байтів.

1. На позиції `i` шукає найдовший збіг із тим, що вже було раніше у вікні.
2. Якщо збіг коротший за 3 байти — видає `Literal(byte)` і зсувається на 1.
3. Інакше видає `Match { distance, length }` і зсувається на `length`.
4. `distance` — на скільки байтів назад почався збіг, `length` — скільки
   байтів копіювати.

Декодер простіший: тримає вихідний буфер, для `Literal` додає байт, для
`Match` копіює `length` байтів із позиції `len - distance`. Копіювати треба
по одному байту, бо збіг може перекривати сам себе.

Приклад: `abcabcabc` → `Literal(a) Literal(b) Literal(c) Match(3, 6)`.

### Підказки по Rust

- Для пошуку збігів зручно мати `Vec<Vec<usize>>` або
  `HashMap<u32, Vec<usize>>`: ключ — перші 3 байти, значення — позиції, де
  вони траплялися.
- Не порівнюй `usize` з `u16` напряму: приводи явно
  (`usize::from(length)`).
- У декодері перевіряй `distance` **до** індексації, інакше буде паніка.
- Для випадкових даних у тестах використовуй `rand::rngs::StdRng` і
  `SeedableRng::seed_from_u64`:
  `use rand::{Rng, SeedableRng};`. У `rand` 0.10 діапазон береться як
  `rng.random_range(0..n)`, а не `gen_range`; `thread_rng()` замінено на
  `rand::rng()`.

### Контракт

```rust
pub const WINDOW: usize = 32_768;
pub const MIN_MATCH: usize = 3;
pub const MAX_MATCH: usize = 258;

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Token {
    Literal(u8),
    Match { distance: u16, length: u16 },
}

/// Стискає дані в послідовність токенів. Не панікує і не повертає помилку.
pub fn encode(data: &[u8]) -> Vec<Token>;

/// Відновлює дані. Будь-який некоректний токен — `ByzError::BadFormat`.
pub fn decode(tokens: &[Token]) -> crate::error::Result<Vec<u8>>;
```

### Вимоги

- `Match { distance, length }` означає: скопіювати `length` байтів, починаючи
  з позиції `output.len() - distance`.
- Перекриття дозволене: при `distance = 1` і `length = 5` байт повторюється
  п'ять разів.
- Кодер видає `Match` лише якщо `MIN_MATCH <= length <= MAX_MATCH` і
  `1 <= distance <= min(WINDOW, уже_виведено_байтів)`.
- Кодер зобов'язаний знаходити збіги ефективно: наївний перебір по всьому вікну
  на 1 МіБ даних неприпустимий. Використовуй хеш-таблицю/ланцюжки за
  3-байтовими ключами.
- Алгоритм: greedy (жадібно беремо найдовший збіг). Lazy matching дозволений,
  якщо не ламає контракт і тести.
- Декодер не довіряє токенам: `distance = 0`, `distance > output.len()`,
  `distance > WINDOW`, `length < MIN_MATCH`, `length > MAX_MATCH` — це
  `ByzError::BadFormat`, без панік.
- Жодного `unsafe`, `unwrap()` або `expect()` у публічних функціях.

### Обов'язкові тести

1. Порожній вхід: `encode(&[])` — порожньо, `decode(&[])` — порожньо.
2. Один байт і два різні байти — round-trip.
3. `b"a" * 10_000`: у токенах є `Match` з `distance == 1`, `length >= 3`;
   round-trip збігається.
4. Текст `"the quick brown fox ...".repeat(...)` — round-trip.
5. Періодичні дані (`"abcabc..."`) — round-trip.
6. 200 випадкових входів із фіксованим seed, довжини `0..5000` — round-trip.
7. Усі токени після `encode` задовольняють інваріанти відстані та довжини.
8. Межа вікна: 32 768 випадкових байтів із фіксованим seed, потім повтор
   перших 300 байтів. Round-trip; жоден токен не має `distance > WINDOW`;
   серед токенів є `Match { distance: 32_768, .. }` — кодер зобов'язаний
   знайти збіг на самій межі вікна, а не тільки не виходити за неї.
9. `decode` відхиляє: `distance = 0`, `distance > output.len()`,
   `distance > WINDOW`, `length = 2`, `length = 259`.
10. 1 МіБ тексту — round-trip (перевірка, що немає катастрофічного
    уповільнення).

### Готово, коли

Стандартний DoD з `AGENTS.md`. Додатково:

- `cargo test lz77` проходить;
- `cargo test --all-targets` не зламаний;
- інтеграція в архіватор **не зроблена** (це окреме завдання власника).

## T-02. Пакування блоків у томи: greedy + DP

**Гілка:** `task/T-02-packing`
**Модуль:** `core/src/packing/mod.rs`
**Дозволено змінювати:** `core/src/packing/**`, `core/src/lib.rs` (+1 рядок)
**Нові залежності:** немає

### Що це і навіщо

Коли архів більший за один том, його треба розрізати на кілька файлів
(томів). Різати можна лише між блоками — файл не можна розірвати навпіл.
Мета — розкласти блоки так, щоб томів було якомога менше: менше файлів,
менше службових даних, простіше збирати архів назад.

### Як це працює

Є розміри блоків `[6, 5, 4, 5]` і місткість тому `10`.

- **Greedy (next-fit):** кладемо блоки в поточний том, поки наступний
  уміщається; інакше відкриваємо новий. Вийде `[6] [5, 4] [5]` — 3 томи.
- **Optimal (DP):** `dp[i]` — мінімальна кількість томів для перших `i`
  блоків. `dp[0] = 0`. Для кожного `i` пробуємо всі `j < i`, де сума блоків
  `j..i` уміщається в том, і беремо `dp[j] + 1` з мінімумом. Відновлюємо
  відповідь за масивом «звідки прийшли». Вийде `[6, 4] [5, 5]` — 2 томи.

Порядок блоків зберігається: том — це неперервний відрізок вихідного масиву.

### Підказки по Rust

- `Vec<Vec<usize>>` — томи з індексами блоків.
- Суми рахуй через `u64::checked_add`, щоб не було переповнення.
- `usize::MAX` зручно використовувати як «нескінченність» у DP.
- Масив «звідки прийшли» — `Vec<Option<usize>>`; `None` означає початок.
- У тестах повний перебір для `n <= 10` пишеться рекурсією, без DP.

### Контракт

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Packing {
    /// Індекси блоків у кожному томі. Порядок блоків у томі й порядок томів
    /// мають відповідати вихідному порядку `sizes`.
    pub volumes: Vec<Vec<usize>>,
}

/// Next-fit: заповнюємо поточний том, поки наступний блок уміщається.
pub fn greedy(sizes: &[u64], capacity: u64) -> crate::error::Result<Packing>;

/// Мінімальна кількість томів. Серед рішень із мінімальною кількістю томів
/// допускається будь-яке коректне.
pub fn optimal(sizes: &[u64], capacity: u64) -> crate::error::Result<Packing>;

impl Packing {
    pub fn volume_count(&self) -> usize;
}
```

### Вимоги

- Блоки не можна переставляти: кожен том — неперервний відрізок вихідного
  масиву. Розбиття — це набір точок розрізу.
- Кожен індекс `0..sizes.len()` зустрічається рівно один раз.
- Сума розмірів у томі не перевищує `capacity`.
- Порядок перевірок: спочатку `capacity`, потім `sizes`. Тому
  `capacity == 0` — завжди `ByzError::BadArgs`, навіть якщо `sizes` порожній.
- Порожній `sizes` (при `capacity > 0`) → `Packing { volumes: vec![] }`.
- Будь-який `size > capacity` → `ByzError::BadArgs`.
- Блоки розміру `0` дозволені.
- Переповнення `u64` під час додавання — `ByzError::BadArgs`, не паніка.
- `optimal` — динамічне програмування за префіксами, `O(n^2)`.
  Жадібний алгоритм для `optimal` не вважається реалізацією.
- `optimal(...).volume_count() <= greedy(...).volume_count()` для будь-яких
  коректних входів.

### Обов'язкові тести

1. Порожній список при `capacity > 0` → `volumes` порожній.
2. Усе вміщається в один том.
3. Точне заповнення (`[5, 5]`, capacity 10).
4. Кожен блок в окремому томі.
5. Блок більший за `capacity` → помилка.
6. `capacity == 0` → помилка; те саме для `greedy(&[], 0)` і `optimal(&[], 0)`.
7. Блоки нульового розміру.
8. Greedy гірший за optimal: `sizes = [6, 5, 4, 5]`, `capacity = 10`.
   Greedy дає 3 томи, optimal — 2.
9. 200 випадкових наборів (`n <= 30`, фіксований seed): результат коректний,
   порядок збережений, `optimal <= greedy`.
10. Для `n <= 10` порівняти `optimal` з повним перебором (рекурсивна функція
    в тестах) — кількість томів має збігатися.
11. Суми поблизу `u64::MAX`: або коректний результат, або `BadArgs`,
    без паніки.

### Готово, коли

Стандартний DoD з `AGENTS.md`; `cargo test packing` проходить; інтеграція у
формат не зроблена.

## T-03. CRC32 (IEEE)

**Гілка:** `task/T-03-crc32`
**Модуль:** `core/src/crc32/mod.rs`
**Дозволено змінювати:** `core/src/crc32/**`, `core/src/lib.rs` (+1 рядок)
**Нові залежності:** немає

### Що це і навіщо

CRC32 — контрольна сума на 32 біти. Вона швидко рахується й дозволяє помітити
пошкодження даних: якщо один байт змінився, сума майже напевно стане іншою.
У zip CRC32 зберігається для кожного файлу; у нас вона знадобиться у
наступній версії формату для перевірки цілісності.

### Як це працює

1. Будуємо таблицю з 256 значень `u32` за поліномом `0xEDB88320`.
2. Стан починається з `0xFFFFFFFF`.
3. Для кожного байта: `index = (state ^ byte) & 0xFF`, потім
   `state = (state >> 8) ^ table[index]`.
4. Наприкінці робимо `state ^ 0xFFFFFFFF` — це і є CRC32.

Контрольний приклад: `crc32("123456789") = 0xCBF43926`. Якщо твій код видає
інше число — таблиця або порядок операцій неправильні.

### Підказки по Rust

- Таблицю можна зробити `const fn` (компілятор порахує її під час збирання)
  або через `std::sync::OnceLock`.
- `u32` підтримує `^`, `>>`, `&` безпосередньо.
- `update` приймає `&[u8]`, тому працює і з масивом, і з `Vec`, і зі
  зрізом.
- `#[derive(Debug, Clone, Copy)]` для структури стану; `Default` реалізуй
  вручну через `new()`.

### Контракт

```rust
#[derive(Debug, Clone, Copy)]
pub struct Crc32 {
    state: u32,
}

impl Crc32 {
    pub fn new() -> Self;
    pub fn update(&mut self, data: &[u8]);
    pub fn finish(&self) -> u32;
}

impl Default for Crc32 {
    fn default() -> Self { Self::new() }
}

/// Одноразовий розрахунок.
pub fn crc32(data: &[u8]) -> u32;
```

### Вимоги

- Алгоритм: CRC-32/IEEE 802.3.
- Відбитий поліном `0xEDB88320`, початкове значення `0xFFFFFFFF`,
  фінальний XOR `0xFFFFFFFF`.
- `Crc32::new()` — початковий стан.
- `update` можна викликати багато разів; результат дорівнює одноразовому
  розрахунку за конкатенацією.
- `finish` не змінює стан і не скидає його.
- Таблиця генерується в `const fn` або один раз ліниво; без `unsafe`.
- Жодних залежностей.

### Обов'язкові тести

1. `crc32(b"") == 0x00000000`.
2. `crc32(b"123456789") == 0xCBF43926`.
3. `crc32(b"a") == 0xE8B7BE43`.
4. `crc32(b"abc") == 0x352441C2`.
5. Інкрементальний розрахунок при **усіх** точках розрізу для `b"123456789"`
   збігається з одноразовим.
6. `Crc32::default()` дає той самий результат, що `new()`.
7. Повторний `finish()` повертає те саме значення.
8. 1 МіБ даних: інкрементально по 4 КіБ == одноразово.
9. Порожні виклики `update(&[])` не змінюють результат.

### Готово, коли

Стандартний DoD з `AGENTS.md`; `cargo test crc32` проходить.

## T-04. MLP-класифікатор + macro-F1

**Гілка:** `task/T-04-mlp`
**Модуль:** `core/src/mlp/mod.rs`
**Дозволено змінювати:** `core/src/mlp/**`, `core/src/lib.rs` (+1 рядок)
**Нові залежності:** немає (можна використовувати вже підключений `rand`)

### Що це і навіщо

MLP (багатошаровий перцептрон) — маленька нейромережа. Їй на вхід дають
вектор чисел (ознаки файлу: ентропія, частка друкованих символів, розмір
тощо), а вона видає ймовірності класів (текст, зображення, архів, …).
Класифікатор потрібен, щоб архіватор сам вибирав стратегію стиснення під тип
файлу.

`macro-F1` — метрика якості: середня F1 по всіх класах. Вона чесніша за
звичайну точність, коли класи нерівномірні.

### Як це працює

Мережа — це шари ваг. Для одного прихованого шару:

1. **Forward:** `z1 = W1 * x + b1`, `h = ReLU(z1)`,
   `z2 = W2 * h + b2`, `p = softmax(z2)`.
2. **Loss:** `-log(p[label])` — перехресна ентропія.
3. **Backward:** обчислюємо градієнти ваг за правилом ланцюжка.
4. **SGD:** `W -= learning_rate * gradient` для всіх ваг одразу після
   перегляду всієї вибірки.

Якщо прихованих шарів кілька, кроки 1 і 3 просто повторюються в циклі:
`ReLU` після кожного прихованого шару, `softmax` — лише на виході. Кількість
шарів задається `sizes`, тому реалізація має бути загальною, а не
захардкоженою під `[n, m, k]`.

`softmax` треба рахувати з відніманням максимуму, інакше `exp` переповниться:
`exp(z - max(z)) / sum(exp(z - max(z)))`.

Приклад для перевірки: XOR. Лінійна модель його не вивчить, а мережа
`[2, 8, 2]` — так.

### Підказки по Rust

- Ваги зручно тримати як `Vec<Vec<Vec<f32>>>`: шар → нейрон → ваги.
- Для ініціалізації використовуй `StdRng::seed_from_u64(seed)` з `rand`.
- Не використовуй зовнішні крейти для матриць: циклів достатньо.
- `f32` швидший і достатній; наприкінці перевіряй, що немає `NaN`
  (`value.is_finite()`).
- `macro_f1` рахуй у `f64`, щоб не накопичувати похибку.

### Контракт

```rust
#[derive(Debug, Clone)]
pub struct Sample {
    pub features: Vec<f32>,
    pub label: usize,
}

#[derive(Debug, Clone)]
pub struct Mlp {
    // поля приватні
}

impl Mlp {
    /// sizes[0] — кількість ознак, sizes.last() — кількість класів.
    /// Мінімум один прихований шар: sizes.len() >= 3.
    pub fn new(sizes: &[usize], seed: u64) -> crate::error::Result<Self>;

    /// Індекс класу з максимальною ймовірністю. За рівності — менший індекс.
    pub fn predict(&self, features: &[f32]) -> crate::error::Result<usize>;

    /// Ймовірності класів, сума 1.0.
    pub fn predict_proba(&self, features: &[f32]) -> crate::error::Result<Vec<f32>>;

    /// Повний batch SGD, перехресна ентропія.
    pub fn train(
        &mut self,
        samples: &[Sample],
        epochs: usize,
        learning_rate: f32,
    ) -> crate::error::Result<()>;
}

/// Macro-F1 за класами 0..classes.
pub fn macro_f1(
    predicted: &[usize],
    expected: &[usize],
    classes: usize,
) -> crate::error::Result<f64>;
```

### Вимоги

- Приховані шари — ReLU, вихід — softmax. Мережа довільної глибини:
  `sizes.len() >= 3`, тобто щонайменше один прихований шар.
- Функція втрат — cross-entropy.
- Ініціалізація ваг детермінована за `seed`.
- `train` — full-batch SGD, без міні-батчів.
- `epochs == 0` — допустимий no-op: передбачення не змінюються. Аргументи
  все одно перевіряються, тому `train(&[], 0, 0.1)` — це `BadArgs`, а не no-op.
- Помилки (`ByzError::BadArgs`): порожній `sizes`, `sizes.len() < 3`, будь-який
  розмір `0`, кількість класів `< 2`, порожній `samples`, довжина `features`
  не збігається з входом, `label >= classes`, `learning_rate` не скінченний
  або `<= 0`.
- `predict` / `predict_proba` перевіряють довжину входу.
- Ймовірності: кожне значення в `[0, 1]`, сума `1.0 ± 1e-5`, без `NaN`.
- Якщо під час `train` ваги або ймовірності стали `NaN`/нескінченними
  (розбіжність), поверни `ByzError::Internal`, а не панікуй.
- `macro_f1`:
  - довжини масивів мають збігатися, інакше `BadArgs`;
  - `classes >= 1`, інакше `BadArgs`;
  - кожна мітка в `predicted` та `expected` має бути `< classes`, інакше
    `BadArgs`;
  - для класу `c`: `tp`, `fp`, `fn`; `f1 = 2*tp / (2*tp + fp + fn)`,
    якщо знаменник `0`, то `f1 = 0.0`;
  - результат — середнє `f1` за всіма `classes`.
- `features`, що містять `NaN` або нескінченність, — `BadArgs`.
- Жодних панік на вхідних даних.

### Обов'язкові тести

1. Помилки конфігурації: `sizes = []`, `[3]`, `[3, 2]` (немає прихованого
   шару), `[3, 0]`, кількість класів 1.
2. `predict` із неправильною довжиною входу → `BadArgs`.
3. `predict_proba`: сума 1, значення в діапазоні, довжина == кількість класів.
4. `predict` збігається з `argmax(predict_proba)`.
5. Детермінізм: два екземпляри з одним `seed` і тими самими даними дають
   однакові ймовірності після навчання.
6. OR: 4 приклади, мережа `[2, 4, 2]`, seed 42, 2000 епох, lr 0.1 —
   точність 100%.
7. XOR: 4 приклади, мережа `[2, 8, 2]`, 10 000 епох, lr 0.1, seed 42 —
   точність 100% (усі 4 приклади). Тест детермінований: якщо обраний seed не
   сходиться, підбери інший seed або збільш кількість епох; тест має бути
   стабільним, а не «іноді зеленим».
8. `epochs = 0` не змінює передбачення.
9. `macro_f1`: ідеальний збіг = 1.0; повний розбіг = 0.0;
   відомий змішаний приклад із точним значенням (порахуй вручну).
10. Помилки `macro_f1`: різна довжина, `classes = 0`, мітка поза діапазоном.
11. Глибока мережа `[2, 4, 4, 2]`: `train` на XOR проходить без паніки,
    `predict_proba` повертає скінченні ймовірності з сумою 1. Точність не
    перевіряємо — важливо, що загальний цикл працює для 3+ шарів.
12. Розбіжність не панікує: `learning_rate = 1e30` на XOR → або
    `ByzError::Internal`, або скінченний результат. Жодної паніки; якщо
    функція повернула `Ok`, то в ймовірностях немає `NaN`.

### Готово, коли

Стандартний DoD з `AGENTS.md`; `cargo test mlp` проходить; інтеграція в
`create` не зроблена.

## T-05. Генетичний алгоритм

**Гілка:** `task/T-05-ga`
**Модуль:** `core/src/ga/mod.rs`
**Дозволено змінювати:** `core/src/ga/**`, `core/src/lib.rs` (+1 рядок)
**Нові залежності:** немає (можна використовувати вже підключений `rand`)

### Що це і навіщо

Генетичний алгоритм шукає добре рішення там, де немає простої формули чи
градієнта. Він тримає популяцію кандидатів (бітові рядки), оцінює кожного
функцією пристосованості й схрещує найкращих. У проєкті GA підбиратиме
параметри архіватора (розмір вікна, пороги, кількість томів), коли повний
перебір неможливий.

### Як це працює

1. Створюємо `population` випадкових бітових рядків довжини `genome_len`.
2. Для кожного рахуємо `fitness(&genome)`.
3. Будуємо нове покоління:
   - копіюємо `elitism` найкращих без змін;
   - для решти вибираємо батьків турніром (випадкові `tournament` особин,
     перемагає найкраща);
   - з імовірністю `crossover_rate` міняємо хвости двох батьків;
   - кожен біт інвертуємо з імовірністю `mutation_rate`.
4. Повторюємо `generations` разів, запам'ятовуючи найкраще значення.

Приклад: OneMax — функція дорівнює кількості одиниць у рядку. Оптимум —
рядок із самих одиниць, `fitness = genome_len`.

### Підказки по Rust

- Функція пристосованості — замикання: `F: Fn(&[u8]) -> f64`.
- Сортування популяції: `individuals.sort_by(|a, b| b.1.total_cmp(&a.1));`.
  `partial_cmp(...).unwrap()` не використовуй: `fitness` може повернути `NaN`,
  і це буде паніка. `f64::total_cmp` працює з будь-якими значеннями.
- Для випадковості — `StdRng` із `seed`; не використовуй `thread_rng`, інакше
  тести стануть недетермінованими.
- `Vec<u8>` для геному; перевіряй, що кожен біт `0` або `1`.
- `history` — `Vec<f64>` довжини `generations`.

### Контракт

```rust
#[derive(Debug, Clone)]
pub struct Config {
    pub population: usize,
    pub generations: usize,
    pub mutation_rate: f64,
    pub crossover_rate: f64,
    pub elitism: usize,
    pub tournament: usize,
    pub seed: u64,
}

#[derive(Debug, Clone, PartialEq)]
pub struct Outcome {
    pub best: Vec<u8>,
    pub best_fitness: f64,
    /// Найкраще значення за весь час після кожного покоління
    /// (best-so-far); довжина == generations.
    pub history: Vec<f64>,
}

pub fn run<F>(
    genome_len: usize,
    config: &Config,
    fitness: F,
) -> crate::error::Result<Outcome>
where
    F: Fn(&[u8]) -> f64;
```

### Вимоги

- Геном — `Vec<u8>`, кожен елемент лише `0` або `1`.
- Ініціалізація випадкова, детермінована за `seed`.
- Відбір — турнірний: випадково вибрати `tournament` особин, узяти найкращу.
- Схрещування — одноточкове, з імовірністю `crossover_rate` на пару.
- Мутація — кожен біт незалежно інвертується з імовірністю `mutation_rate`.
- Елітизм — найкращі `elitism` особин переходять у наступне покоління без змін.
- `history[i]` — найкраще значення **за весь час** після покоління `i`
  (best-so-far), а не лише найкраще в цьому поколінні. Тому `history` не
  спадає навіть при `elitism == 0`.
- `best_fitness == history.last()` (поколінь завжди хоча б одне).
- `best` і `best_fitness` — найкраща особина за весь час, а не лише останнє
  покоління.
- `fitness` викликається лише зі зрізами довжини `genome_len`.
- Помилки (`ByzError::BadArgs`): `genome_len == 0`, `population < 2`,
  `generations == 0`, `elitism > population`, `tournament == 0` або
  `tournament > population`, `mutation_rate`/`crossover_rate` поза `[0, 1]`
  або не скінченні. `elitism == population` і ймовірності `0` — допустимі:
  тоді покоління просто не змінюється.
- Жодних панік на вхідних даних.

### Обов'язкові тести

1. Усі варіанти некоректного `Config` → `BadArgs`.
2. OneMax: `genome_len = 64`, population 100, generations 200,
   mutation 0.02, crossover 0.9, elitism 2, tournament 3, seed 42.
   `best_fitness == 64.0`. Якщо конкретний seed не сходиться за 200 поколінь,
   збільш `generations` або підбери інший seed — тест має бути стабільним,
   а не «іноді зеленим».
3. `history.len() == generations` і `history` не спадає. Перевір це окремо
   для `elitism = 0`: монотонність має триматися завдяки best-so-far, а не
   елітизму.
4. `best` складається лише з `0`/`1`, довжина `genome_len`.
5. Детермінізм: два запуски з одним seed дають однаковий `Outcome`.
6. `fitness` отримує зрізи правильної довжини (перевірити всередині замикання).
7. Елітизм: за постійної функції пристосованості найкраще значення не
   погіршується.
8. `mutation_rate = 0`, `crossover_rate = 0`: алгоритм не панікує, елітизм
   зберігає найкращу особину.

### Готово, коли

Стандартний DoD з `AGENTS.md`; `cargo test ga` проходить; GA не вбудований у
створення архівів.
